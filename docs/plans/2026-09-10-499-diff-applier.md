# #499 diff-applier — build plan

Executes the approved design in `2026-09-10-diff-applier-design.md`. That doc
holds the *why*, the measured first diff and the decisions; this one holds the
order of work and what "done" looks like at each step.

## Problem

The desired state exists (#497) and nothing reads it. Until something diffs it
against live Postgres, the epic's safeguards — dry runs until clean, abort
thresholds, one supervised triage pass — are words: the clean-run streak that
#501 waits on cannot start, and the 24 person-name, 26 acronym and 4 parent
disagreements the first dry run will surface stay unmeasured on the nightly
schedule. #500's archive-on-absence has nothing to attach to.

## Approach

A manifest-driven engine in `src/core/ingestion/applier.py` interpreting four
binding shapes (`entity`, `column`, `child`, `merge`) declared per table in
`manifest.yml` v2; row scope read from the live crosswalk; a typed diff with
stable entry ids; thresholds, verdicts, a report artifact and a run ledger; a
writer that emits minimal SQL in one transaction and re-diffs inside it before
commit; a `scripts/` CLI under the house rules; a 09:30 UTC oneshot chain
(export → build → apply). Every step is red-then-green and its own commit.

## Tradeoffs / alternatives

Settled in the design doc; restated so a reviewer of this plan need not open it.

- **One Python applier class per table** — rejected: nine now, more with #500,
  and the manifest decays into documentation instead of the contract.
- **Diff in SQL via temp tables** — rejected: a live-database dependency where
  the design kept files, and engine tests that need a database.
- **Always update the canonical child row** — rejected: 66 org display-name
  renames PM chose on purpose. **Insert-if-absent** — rejected: the 24
  disagreements never surface. Chosen: present anywhere satisfies, else the
  canonical row is the one in dispute.
- **Act on merges now** — deferred to #514: zero real tombstones to test on.

## Steps

1. **Manifest v2 and build provenance.** `manifest.yml` gains `version: 2`,
   top-level `thresholds:` + `streak:`, and a `target:` block per table (shape,
   table, parent/columns/match/insert defaults/lookups as the shape needs); a
   typed loader (`Manifest`, `TableSpec`, `Target`) rejects an unknown shape or
   a binding missing what its shape requires. `build_desired_state` writes
   `data/desired_state/BUILD.json` (dataset versions from `source_env`,
   crosswalk export digest, built-at). *Done:* `test_manifest.py` gates every
   table's target; the fixture build writes `BUILD.json` and the unit test
   reads it back.
2. **Engine inputs and scope.** `DesiredState.load(dir)`; the `LiveStore`
   protocol (`crosswalk`, `entity_rows`, `child_rows`, `lookup`) and a
   dict-backed `FakeLiveStore` under `tests/`; `Scope` built from the live
   crosswalk; `stale` when a desired `pm_id` disagrees or its row left scope.
   *Done:* `tests/core/ingestion/test_applier_scope.py` — in-scope, stale on
   drift, stale on resolution change, out-of-scope rows invisible.
3. **Diff, entity and column shapes.** `Entry(entry_id, table, kind, pm_id,
   producer_id, changes, hint)` with kinds `noop/create/update/retract/stale/
   conflict/merge`; entity existence and archived-as-stale; creates carrying
   the same-value hint; report-only retraction; column compare. *Done:*
   `test_applier_diff.py` covers each kind for both shapes with the fake.
4. **Diff, child shapes.** `any_then_canonical` in its three outcomes plus the
   no-canonical insert; `key` for events (none/one/many; owned types only;
   report-only retraction of an owned type); lookups resolved through the
   store. *Done:* the measured cases from the design are fixtures — the
   short/long org name is a `noop`, the curly-quote person name an `update` of
   the canonical, a second dissolved event a `conflict`.
5. **Thresholds, verdict, artifact, ledger, gate.** `Thresholds` from the
   manifest with CLI overrides; verdict `clean/blocked/stale`; `diff.jsonl`
   with stable ids and a digest over sorted actionable entries;
   `summary.json`/`summary.md`; `ledger.jsonl` append; `may_execute(ledger,
   run)` — last `streak` dry runs clean with the same digest, and the current
   run reproduces it. *Done:* digest invariant under row order; the gate on
   fixture ledgers (short streak, a blocked night, a changed digest, all
   refuse).
6. **Writer and the transaction.** Statements per entry in order (entity
   creates → child rows → columns), the crosswalk row on create, a
   `StatementRecorder` for tests; `apply(execute=True)`: transaction →
   statements → re-diff → empty or rollback. *Done:* the two acceptance proofs
   on emitted SQL — an unowned column never appears in an `UPDATE`, an
   out-of-scope row yields no statement — plus "the re-diff after the
   recorder's statements is empty".
7. **The CLI and the Postgres store.** `scripts/apply_desired_state.py`
   (`add_dsn_args`, `resolve_dsn`, dry run default, `--execute`,
   `--allow-creates`, `--max-updates`, `--streak`, `--desired`, `--out`); exit
   codes dry 0/3, execute 0/1; `PostgresLiveStore` on asyncpg. *Done:* the
   DSN sweep passes on the new script; exit-code tests through a stubbed
   engine.
8. **Integration tier.** `tests/scripts/test_apply_desired_state.py`
   (`-m integration`): a seeded world on the rollback connection with the
   desired state written to Parquet in `tmp_path`; apply twice is a no-op; a
   gated create aborts with zero rows changed; `--execute` writes exactly the
   predicted entries and outbox rows appear; `people.notes` survives a name
   update; a person outside the crosswalk survives a desired row naming it; a
   cyclic parent rolls the run back; a crosswalk change between build and
   apply is `stale`. *Done:* green on `TEST_DATABASE_URL`.
9. **The nightly chain.** `infra/power-map-desired-state.service` (oneshot,
   three `ExecStart=` lines under `uv run --group mapping`) + `.timer` (09:30
   UTC, `Persistent=true`); a structural test pins the three steps, their
   order and the group. *Done:* the test; installation is a ship step.
10. **Docs, version, ship.** `RUNBOOKS.md` § Apply the desired state (the
    verdicts, reading `diff.jsonl`, the flip's flags); `COMMANDS.md` timers
    row; `TESTING.md` applier tier; `SCHEMA.md` § Producer crosswalk (the
    applier writes creates); 0.47.0. Ship: PR, merge, restart, install and
    enable the timer, then the first operator dry run against production —
    its report should say what the design's table says, and its ledger line
    is night one of the streak.

## Open questions / risks

- **`updates` is unthresholded by default.** The first `--execute` (#501) would
  apply every pending update at once; #501 passes `--max-updates` for the
  flip. Fine for #499, worth stating.
- **The nightly chain mutates production's venv.** `uv run --group mapping` in
  the main checkout adds the group to the service's environment each night and
  the service's next `uv sync` removes it — additive while running, so safe,
  and already the documented pattern for the operator run. A per-chain venv
  would end the churn; not this issue.
- **Fake-store fidelity.** Matching semantics live in Python, so the fake is
  faithful by construction; what the fake cannot prove — triggers, cycles,
  the outbox — is exactly step 8's list.
- **Entry ids for creates use `producer_id`** (there is no `pm_id`); once a
  create is applied the same producer row's future entries carry the new
  `pm_id` in the entry body but the same id — stable across the flip.
